브라우저는 새 프레임을 화면에 그릴 준비가 될 때마다 `video.requestVideoFrameCallback`을
호출한다. 60fps 영상에서는 16.67ms마다 새 프레임이 들어온다. 모든 프레임을 분석하려면 프레임
하나의 전처리와 추론을 평균 16.67ms 안에 끝내야 한다.

이보다 오래 걸리면 이전 프레임을 처리하는 동안 새 프레임이 들어온다. 메인 스레드에서 이전 프레임을
처리 중이면 프레임 콜백을 받지 못할 수 있다. 워커가 처리 중이면 기다리던 프레임을 새 프레임으로
바꾸므로 이전 대기 프레임은 처리하지 않는다. 앞선 실험에서는 30fps 영상을 50초 재생하며 화면 갱신
콜백과 프레임 콜백에서 각각 40ms의 작업을 실행했고, `requestVideoFrameCallback`이 중간 프레임
856개를 받지 못했다.

다음 실험에서는 실제 모델 여러 개의 실행 시간과 결과를 비교한다. 그 전에 전처리를 어디에서 어떤
방법으로 실행할지 정하고, 프레임마다 전처리에 몇 ms가 필요한지 알아야 했다. 이를 확인하려고 축소
방법(캔버스, 직접 계산, `createImageBitmap`)과 스레드(메인, 워커)를 조합해 A\~D의 전처리 방법을
만들고 각각 얼마나 걸리는지 쟀다. 같은 조건에서 300프레임씩 두 번 돌렸다. 카메라를 열고 프레임을
받아오는 시간은 이번 측정에서 뺐다.

## 비교한 전처리 방법

카메라 프레임은 모델에 바로 넣을 수 없다. 카메라가 제공하는 프레임과 모델이 요구하는 입력은
크기와 데이터 형식이 다르기 때문이다. 이번 실험에서 실제로 받은 프레임은 1920×1080이었고,
다음 모델 비교에서 사용할 기준 형식인 224×224 RGB 값을 담은 `Float32Array`로 변환했다. 실제
모델이 다른 자료형이나 배열 배치를 요구하면 다음 실험에서 마지막 배열 변환을 그 형식에 맞춘다.

프레임 가운데를 정사각형으로 잘라 224×224로 줄였다. 그런 다음 투명도 값을 빼고, 각 색상의
0부터 255까지의 정수를 0부터 1까지의 32비트 부동소수점 수로 바꿨다.

A\~D는 모두 같은 규격의 모델 입력 배열을 만든다. A\~D에서 **프레임을 줄이는 과정**과
**전처리 코드를 실행하는 스레드**는 서로 다르다.

브라우저는 메인 스레드에서 화면 갱신, 사용자 입력과 페이지의 JavaScript를 차례로 처리한다.
메인 스레드에서 한 작업을 오래 실행하면 그동안 화면 갱신과 사용자 입력 처리가 늦어진다. 워커에서는
메인 스레드와 별도로 JavaScript를 실행할 수 있다.

- **A: 캔버스에 바로 작게 그린다.**
  카메라 프레임의 가운데 부분을 224×224 캔버스에
  `drawImage`로 그린다. 이때 브라우저가 자르기와 축소를 함께 처리한다. 이어서 픽셀을 읽고 모델
  입력 배열로 바꾼다. 이 작업을 요청하고 결과를 읽는 코드는 모두 메인 스레드에서 실행된다.
- **B: JavaScript 코드로 직접 줄인다.**
  먼저 카메라 프레임의 1920×1080 픽셀을 모두 읽는다.
  그런 다음 JavaScript 반복문으로 주변 픽셀을 섞어 224×224로 만든다. A\~D 중 B만 원본
  픽셀 전체를 읽고 축소 계산까지 직접 한다.
- **C: A와 같은 작업을 워커에서 실행한다.**
  자르기, 축소, 픽셀 읽기와 배열 변환 방법은 A와 같다.
  다만 프레임을 워커로 넘기고 그곳에서 처리하므로 메인 스레드에서 전처리 코드를 실행하는 시간이
  짧다.
- **D: 먼저 비동기 API로 줄인다.**
  `createImageBitmap`에 자르기와 축소를 요청하고 기다린다.
  축소된 224×224 이미지가 돌아오면 캔버스에 같은 크기로 그리고, 픽셀을 읽어 모델 입력 배열로
  바꾼다.

가장 단순한 A의 코드는 이렇다. 카메라 프레임을 224×224 크기로 캔버스에 그린 뒤, 픽셀 값을
읽어 모델 입력 배열로 바꾼다.

```js
// 가운데를 잘라 224×224 캔버스에 그린다
ctx.drawImage(frame, 420, 0, 1080, 1080, 0, 0, 224, 224);

// 캔버스에 그려진 픽셀 값을 읽는다
const pixels = ctx.getImageData(0, 0, 224, 224);

// 픽셀 값을 이번 실험의 입력 배열로 바꾼다
const input = toModelInput(pixels);
```

`toModelInput`은 `getImageData`로 읽은 RGBA 픽셀에서 투명도 값을 제외하고, RGB의 0\~255 값을 이번
실험의 기준인 0\~1 값으로 바꾸는 함수다.

|     | 프레임을 줄이는 방법       | 픽셀 읽기와 배열 변환 | 읽는 픽셀 수           |
| --- | -------------------------- | --------------------- | ---------------------- |
| A   | 캔버스에 바로 작게 그리기  | 메인                  | 224×224                |
| B   | JavaScript로 직접 계산     | 메인                  | **1920×1080** (8.29MB) |
| C   | A의 작업을 워커에서 처리   | 워커                  | 224×224                |
| D   | `createImageBitmap`에 요청 | 메인                  | 224×224                |

**실험 조건.** macOS의 Chrome 151에서 USB로 연결한 아이폰 14 Plus의 연속성 카메라를
사용했다. 카메라는 1920×1080, 60fps로 설정했고, 실험에 사용한 실행에서는 실제 입력도
59.8\~60.1fps였다. 각 프레임의 가운데를 정사각형으로 잘라 224×224 모델 입력 배열로 바꿨다.
A\~D를 각각 300프레임씩 두 번 측정했다.

## 측정 항목

같은 전처리가 4ms 걸리더라도 메인 스레드에서 처리하면 그동안 화면을 갱신하거나 클릭에 반응할
수 없다. 워커에서 처리하면 모델 입력이 완성되는 데는 여전히 4ms가 걸리지만, 그동안 메인
스레드는 화면을 갱신하고 클릭을 처리할 수 있다. 그래서 다음 두 시간을 따로 쟀다.

| 측정값                    | 재는 구간                                           | 답하려는 질문                                                   |
| ------------------------- | --------------------------------------------------- | --------------------------------------------------------------- |
| **메인 스레드 실행 시간** | 전처리 코드가 메인 스레드에서 실행된 시간의 합      | 그동안 화면 갱신과 사용자 입력을 처리하지 못한 시간은 얼마인가? |
| **전처리 지연**           | 프레임을 얻은 때부터 모델 입력 배열이 완성될 때까지 | 모델이 추론을 시작하려면 얼마나 기다려야 하는가?                |

워커가 처리하는 시간이나 `createImageBitmap`의 결과를 기다리는 시간은 전처리 지연에는 들어간다.
하지만 기다리는 동안 메인 스레드는 다른 일을 할 수 있으므로 메인 스레드 실행 시간에는 들어가지
않는다.

### `drawImage`의 시간만 재서는 축소 시간을 알 수 없다

`drawImage` 호출이 끝나도 브라우저의 자르기와 축소 작업은 남아 있을 수 있다. 이후
`getImageData`를 호출하면 브라우저는 남은 작업을 끝낸 뒤 픽셀 값을 반환한다. 따라서
`getImageData`에서 잰 시간에는 픽셀을 읽는 시간뿐 아니라 앞선 자르기와 축소를 기다린 시간도
포함될 수 있다. 이 실험에서는 두 호출을 따로 해석하지 않고, 전체 메인 스레드 실행 시간과 전처리 지연을
비교했다.

## 측정값 계산 방법

메인 스레드와 워커에서 기록한 시각은 바로 비교하지 않았다. 카메라 프레임을 측정하기 전에 메시지를
30번 왕복시켰다. 응답 시간이 가장 짧았던 기록으로 두 시각의 차이를 계산하고, 워커가 기록한 시각을
메인 스레드의 기준에 맞췄다.

메인 스레드 실행 시간에는 전처리 코드를 실행한 시간과 `postMessage`를 호출한 시간을 포함했다.
C는 전처리를 워커에서 실행하므로 메인 스레드에서는 `postMessage`를 호출한 0.1ms만 측정됐다.

데이터 전달 시간은 메인 스레드가 `postMessage`를 호출하기 직전부터 워커가 메시지 처리를 시작할
때까지로 계산했다. C의 워커 전처리 시간은 데이터 전달 시간에 포함하지 않고 전처리 지연에 포함했다.

## 이 실험에서 다음 결과를 확인했다

- JavaScript로 직접 축소한 B의 메인 스레드 실행 시간은 8.1ms였다. 캔버스를 사용한 A의
  3.8ms보다 두 배 이상 길었다.
- C의 전처리 지연은 4.4ms로 A의 3.9ms와 비슷했다. 메인 스레드 실행 시간은 A의 3.8ms에서
  C의 0.1ms로 감소했다.
- D와 A는 두 번의 측정에서 순서가 바뀌었다. 어느 쪽이 빠른지 판단할 수 없었다.
- 픽셀 배열을 변환한 `toModelInput`에는 0.2\~0.4ms가 걸렸다. 전체 전처리 시간의 10% 미만이었다.
- `willReadFrequently`를 켜면 세 호출의 합이 2.2\~3.0ms 증가했다.
- 데이터를 워커로 보내는 시간의 p95는 A\~D 모두 0.3ms 이하였다.
- C의 워커 전처리 p50은 부하가 없는 조건에서 4.1ms, 20ms의 CPU 작업을 추가한 조건에서
  1.7ms였다.
- 워커가 20ms 동안 다른 작업을 실행할 때 가장 최근 프레임 하나만 보관하는 규칙이 적용됐다.

## A\~D의 측정값을 비교했다

### 변환 결과 비교

시간을 재기 전에 결과부터 맞춰야 한다. 결과가 다르면 시간 비교가 성립하지 않는다.
고정된 그림 하나를 넣어 배열을 비교했다.

| 비교  | 픽셀 값 최대 차이 (0\~255) |
| ----- | -------------------------- |
| A ↔ B | 3.0                        |
| A ↔ C | **0.0**                    |
| A ↔ D | 2.0                        |

같은 캔버스 축소를 쓰는 A와 C는 픽셀 값까지 완전히 같았다. B와 D는 축소 방법이 달라 최대
2\~3만큼 차이 났다. 한 색상 값이 가질 수 있는 0\~255 범위에서 이 정도 차이는 허용하고 시간을
비교했다.

### 전처리 시간 비교

방식마다 두 번 측정했다. p50은 전체 프레임의 절반이 이 시간 안에 끝났다는 뜻이고, p95는
95%가 이 시간 안에 끝났다는 뜻이다. 가끔 크게 튀는 프레임이 평균을 끌어올릴 수 있어서 평균 대신
두 값을 사용했다. 아래 표의 p50은 두 실행을 모두 표시하고, p95는 2회차 값을 표시한다.

| 측정값 (ms)                   | A 캔버스    | B JavaScript | C 워커      | D `createImageBitmap` |
| ----------------------------- | ----------- | ------------ | ----------- | --------------------- |
| 메인 스레드 실행 p50, 1회/2회 | 4.10 / 3.80 | 8.10 / 8.10  | 0.10 / 0.10 | 3.90 / 4.20           |
| 메인 스레드 실행 p95, 2회     | 4.90        | 8.70         | 0.20        | 5.40                  |
| 전처리 지연 p50, 1회/2회      | 4.20 / 3.90 | 8.10 / 8.20  | 4.20 / 4.40 | 4.10 / 4.40           |
| 전처리 지연 p95, 2회          | 5.00        | 8.80         | 5.50        | 5.70                  |

표에서 세 가지를 확인했다.

- **B는 A보다 두 배가량 느리다.** B는 1920×1080 픽셀 8.29MB를 모두 읽은 뒤 JavaScript로
  직접 줄인다. A보다 약 4ms를 더 써서 후보에서 제외했다.
- **C는 전처리를 더 빨리 끝내지는 않지만 메인 스레드에서 실행되는 시간은 짧다.** 전처리 지연은
  4.40ms로 A의 3.90ms와 비슷하지만, 메인 스레드 실행 시간은 3.80ms에서 0.10ms로 줄었다.
  4.1ms의 전처리 작업은 그대로 실행됐고 실행 위치만 메인 스레드에서 워커로 바뀌었다.
- **D는 A보다 빠르다고 볼 수 없다.** 메인 스레드 실행 시간의 p50은 1회차에는 D가 A보다 0.20ms
  작았지만, 2회차에는 반대로 D가 0.40ms 컸다. 두 측정에서 순서가 뒤집혀 이 자료만으로는
  A와 D 중 어느 쪽이 빠른지 판단할 수 없다.

같은 코드를 두 번 실행했을 때도 p50이 최대 0.3ms 달랐다. 따라서 두 전처리 방법의 차이가
0.3ms 이하이면 어느 쪽이 빠르다고 판단하지 않았다.

C가 전처리를 더 빨리 끝내지는 않았다. A와 같은 약 4.1ms의 작업을 메인 스레드에서 워커로
옮겼기 때문에 메인 스레드에서 전처리 코드를 실행한 시간만 줄었다. 워커에서는 페이지의 캔버스를
사용할 수 없어서 워커용 캔버스인 `OffscreenCanvas`로 같은 작업을 했다.

### D의 축소 요청 전후 비교

| 구간                                              | 1회차 p50 | 2회차 p50 |
| ------------------------------------------------- | --------- | --------- |
| 축소를 요청하고 결과를 기다리기 전까지            | 0.30ms    | 0.30ms    |
| 결과가 온 뒤 캔버스에 그리고, 읽고, 배열로 바꾸기 | 4.10ms    | 3.90ms    |

앞 구간의 0.30ms는 축소가 끝나는 데 걸린 시간이 아니다. `createImageBitmap`에 작업을 요청하고
기다리기 시작할 때까지 메인 스레드가 쓴 시간이다. 실제 축소는 기다리는 동안 진행된다. 결과가
온 뒤의 3.90\~4.10ms만으로도 A의 전체 메인 스레드 실행 시간과 비슷했다. 따라서 이번 측정에서는 축소 작업을
비동기 API로 분리한 D의 이점을 확인하지 못했다.

완료 fps와 입력 fps는 결과에서 제외했다. 이 실행들은 fps 계산을 고치기 전에 측정해서 저장된
카운터로 값을 재현할 수 없었다. 위의 시간값과 결과 배열 비교에는 이 오류가 영향을 주지 않는다.

### 워커 전달 시간

C는 전처리 전의 `VideoFrame`을 워커로 보내고, A·B·D는 전처리가 끝난 모델 입력 배열을 보낸다.
이번 실험에서는 데이터를 복사하지 않고 워커가 이어서 쓰도록 넘겼다. 메시지를 보낸 때부터 워커가
받기까지 걸린 시간의 p95는 A\~D 모두 0.3ms 이하였다. 약 4ms인 전처리 시간보다 작아서 방식
선택을 바꿀 정도는 아니었다. C의 한 실행에서만 0.4ms와 1.4ms가 한 번씩 나왔다.

## 픽셀 배열 변환 시간을 따로 쟀다

앞의 비교에서는 A의 전처리에 약 4ms가 걸렸다. 이번에는 그중 픽셀 배열을 변환하는 반복문에
몇 ms가 필요한지 확인했다.

### 세 단계를 모두 실행하며 각 구간의 시간을 쟀다

A의 `drawImage`, `getImageData`, `toModelInput`을 프레임마다 모두 실행하고 각 호출의 앞뒤에서
시각을 기록했다. 세 호출을 모두 실행한 이유는 `drawImage` 호출 시간만으로 그리기와 축소가
완료된 시간을 알 수 없기 때문이다.

`willReadFrequently` 값에 따라 브라우저가 캔버스를 처리하는 방법이 달라질 수 있다.
`toModelInput`은 캔버스를 사용하지 않는다. 캔버스 호출 구간과 배열 변환 구간을 비교하려고
옵션을 끈 조건과 켠 조건을 각각 두 번씩 실행했다.

### 배열 변환에는 0.2\~0.4ms가 걸렸다

| 구간 p50 (ms)       | 끔 (1회차 / 2회차) | 켬 (1회차 / 2회차) |
| ------------------- | ------------------ | ------------------ |
| `drawImage` 호출    | 0.30 / 0.30        | **6.90 / 6.60**    |
| `getImageData` 호출 | **4.10 / 3.30**    | 0.10 / 0.10        |
| `toModelInput`      | 0.40 / 0.40        | 0.20 / 0.20        |
| 합                  | 4.80 / 4.10        | 7.10 / 6.90        |

`toModelInput` 호출 구간은 두 조건에서 0.2\~0.4ms였다. 전체 실행 시간과 비교하면 10% 미만이다.
이 함수의 실행 시간을 0으로 줄여도 프레임당 줄어드는 시간은 최대 0.4ms다. 전처리 시간을 더 줄일
방법을 찾으려면 `drawImage`와 `getImageData`를 사용하는 현재 방법을 다른 방법과 비교해야 한다.

`willReadFrequently`를 켜면 세 호출의 합이 4.1\~4.8ms에서 6.9\~7.1ms로 증가했다. 이후 실험에서는
이 옵션을 켜지 않았다.

### 그리기와 픽셀 읽기에 걸린 시간은 따로 알 수 없었다

옵션을 끄면 `getImageData` 호출 구간은 3.3\~4.1ms였고, `drawImage` 호출 구간은 0.3ms였다.
옵션을 켜면 반대로 `drawImage` 호출 구간은 6.6\~6.9ms였고, `getImageData` 호출 구간은 0.1ms였다.

이 값은 실제 그리기 시간과 실제 픽셀 읽기 시간을 각각 나타내지 않는다. 브라우저는
`drawImage`에서 시작한 작업을 `getImageData`를 실행할 때 완료할 수 있다. Canvas 2D API는
브라우저가 각 작업을 언제, 어디에서 처리했는지 제공하지 않는다. 따라서 두 캔버스 호출을 합친
시간과 배열 변환 시간은 비교할 수 있지만, 그리기와 픽셀 읽기에 필요한 시간은 각각 구할 수 없었다.

## 이번 실험에서 비교하지 않은 방법과 환경

### GPU의 전처리 결과를 모델에 직접 넣는 방법은 비교하지 않았다

`toModelInput` 실행 시간은 전체 전처리 시간의 10% 미만이었다. 나머지 대부분은 `drawImage`와
`getImageData` 호출 구간에 포함됐다. Canvas 2D API만으로는 두 작업의 실제 시간을 구분할 수
없었다.

WebGPU에서는 카메라 프레임을 GPU에서 자르고 줄인 뒤, 모델 입력 형식으로 변환한 결과를 GPU 버퍼에
저장할 수 있다. 모델 실행기가 이 버퍼를 직접 입력으로 받는다면 `drawImage`, `getImageData`와
CPU의 `Float32Array` 생성을 생략할 수 있다. 모델이 CPU의 `Float32Array`만 받는다면 GPU의 결과를
다시 CPU로 읽어야 하므로 같은 이점을 기대할 수 없다. 이번 실험에서는 CPU의 `Float32Array`를
만드는 방법만 비교했으며, GPU 버퍼를 직접 입력하는 방법은 다음 모델 비교를 시작하기 위한 조건에
포함하지 않았다.

### 다른 브라우저와 기기는 측정하지 않았다

A\~D의 변환 결과는 Chrome 151과 macOS에서 비교했다. Canvas 2D 표준은 축소 계산 방법을 하나로
정하지 않으므로, 다른 브라우저와 기기에서는 픽셀 값과 실행 시간을 다시 측정한다.

## 다음 모델 비교 실험에서 사용할 방법

### 전처리는 워커에서 실행한다

C의 전처리 지연은 A와 비슷했지만, 메인 스레드 실행 시간은 3.8ms에서 0.1ms로 감소했다. 다음
모델 실험에서는 C처럼 전처리를 워커에서 실행한다.

워커를 사용하려면 메인 스레드와 메시지를 주고받아야 한다. 전송 시간을 측정할 때 사용한 시각 차이
계산은 실험용 코드이며, 실제 전처리에는 필요하지 않다.

### 자르기와 축소에는 `drawImage`를 사용한다

원본 영상의 가운데 정사각형 영역을 224×224 크기의 `OffscreenCanvas`에 `drawImage`로 그리면
브라우저가 자르기와 축소를 함께 처리한다.

B는 먼저 1920×1080 프레임 전체를 캔버스에서 읽었다. 이어서 `resizeBilinear`가 224×224의 각
픽셀에 대응하는 원본 위치를 계산하고, 그 위치 주변의 네 픽셀을 비율에 따라 섞었다. 가운데 영역을
선택하는 작업도 이 함수에서 처리했다. 마지막에는 이 RGBA 결과에서 투명도 값을 빼고 RGB 값을
담은 `Float32Array`로 변환했다.

이 과정을 메인 스레드에서 실행한 B의 실행 시간은 8.1ms로, 캔버스가 자르기와 축소를 처리한 A의
3.8ms보다 두 배가량 길었다. 따라서 다음 모델 실험에서는 B의 JavaScript 축소 코드를 사용하지 않고,
워커의 `OffscreenCanvas`와 `drawImage`로 자르기와 축소를 처리한다.

### 워커가 처리 중이면 가장 최근 프레임만 남긴다

카메라는 초당 약 60개의 프레임을 보낸다. 워커가 이 속도보다 느린데도 모든 프레임을 순서대로
저장하면, 워커는 오래전에 촬영된 프레임을 계속 처리하게 된다. 이를 막기 위해 워커가 처리할 프레임
한 개와 기다릴 프레임 한 개만 보관한다.

예를 들어 워커가 1번 프레임을 처리하는 동안 2번 프레임이 들어오면 2번을 보관한다. 1번 처리가
끝나기 전에 3번 프레임이 들어오면 2번을 버리고 3번을 보관한다. 워커는 1번 처리를 끝낸 뒤 3번을
처리한다. 이후에도 같은 규칙을 적용한다.

이 규칙이 실제로 동작하는지 확인하려고 워커가 프레임 하나를 처리할 때마다 20ms 동안 CPU 작업을
실행했다. 카메라에서 초당 60.0개의 프레임이 들어왔고, 워커는 초당 46.1개를 처리했다. 나머지
13.9개는 다른 프레임을 처리하는 동안 더 새로운 프레임이 들어와서 버렸다. 처리 결과에는 때때로
1번 다음에 3번이 나왔다. 워커는 중간의 2번 프레임을 나중에 처리하지 않았다.

### 실제 모델을 비교할 때 전처리 시간도 함께 기록한다

워커가 전처리만 실행한 기본 조건에서 전처리 작업의 p50은 4.1ms였다. 최신 프레임 관리 코드를
확인하려고 20ms의 CPU 작업을 추가한 조건에서는 1.7ms였다. 두 값이 다르므로 4.1ms는 부하가 없는
조건의 측정값이며, 실제 모델을 실행할 때의 고정값으로 사용하지 않는다.

다음 모델 비교에서는 위에서 정한 전처리 방법을 사용하고, 각 모델을 실행하는 동안 전처리 시간과
모델 실행 시간을 각각 기록한다.
