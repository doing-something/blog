60fps에서는 새 프레임이 약 16.7ms마다 들어온다. 앞선 실험에서 프레임을 모델 입력으로 바꾸는 데 4.1ms가 걸렸다.
모든 프레임을 분석하려면 모델 추론은 약 12.6ms 안에 끝나야 한다.

TensorFlow.js는 같은 모델의 계산을 CPU, WebAssembly(WASM), WebGL, WebGPU 중 하나로 실행할 수 있다.
이처럼 모델의 계산을 실제로 수행하는 방식을 TensorFlow.js에서는 ‘백엔드’라고 부른다.
이번에는 이미지를 분류하는 모델인 MobileNet v2를 CPU, WASM, WebGL, WebGPU로 각각 실행해 다음 항목을 측정했다.

- 모델을 불러오는 데 걸린 시간
- 모델을 불러온 뒤 처음 실행한 추론 시간
- 반복 추론 시간과 실행 초반의 변화
- 전처리와 추론을 합친 전체 시간
- `predict()`가 JavaScript를 점유한 시간

모델이 프레임 입력 속도를 따라가지 못하면 처리할 프레임이 쌓인다.
쌓인 프레임을 순서대로 처리하면 분석 결과가 현재 영상보다 늦어진다.
다음 실험에서는 밀린 프레임을 모두 처리하지 않고 가장 최근 프레임 하나만 남기는 방식을 적용한다.
이를 고려해 이번 실험에서는 결과가 나오기까지의 시간과 JavaScript가 점유되는 시간을 따로 측정했다.

## 같은 MobileNet 모델을 CPU, WASM, WebGL, WebGPU로 실행했다

실험에는 TensorFlow.js 4.22.0과 TensorFlow Hub의 MobileNet v2 모델
`mobilenet_v2_100_224/classification/2`를 사용했다. 모델 파일의 전체 크기는 약 13.3MB다.

이 모델은 224×224 크기의 RGB 이미지 한 장을 입력받는다. 각 RGB 값은 0에서 1 사이이며, 모델은 1,001개 항목의 분류 점수를 출력한다.

공식 MobileNet 패키지는 모델을 불러오는 과정에서 추론을 한 번 미리 실행한다. 그러면 이후에 측정한 첫 추론은 실제로는 두 번째 실행이 된다.
이 실험에서는 첫 실행 시간을 따로 재기 위해 공식 패키지를 사용하지 않고 모델을 직접 불러왔다. CPU, WASM, WebGL, WebGPU 모두 다음과 같은 코드로 추론했다.

```js
const model = await tf.loadGraphModel(MODEL_URL, {
  fromTFHub: true,
});

const input = tf.tensor4d(values, [1, 224, 224, 3]);
const output = model.predict(input);
await output.data();

output.dispose();
input.dispose();
```

측정 환경은 macOS, Chrome 151, Apple M4다.
CPU, WASM, WebGL, WebGPU에서 동일한 입력을 각각 50번 실행했다.
첫 추론 시간은 별도로 기록했다. 반복 추론 시간은 처음 5번을 제외한 나머지 45번으로 계산했다.
또한 50번을 5번씩 나눠 실행 시간이 계속 변하는지도 확인했다.
WebGL, WebGPU, WASM은 세 차례, CPU는 두 차례 측정해 실행마다 결과가 얼마나 달라지는지도 확인했다.

## `predict()`가 반환돼도 GPU 계산은 끝나지 않을 수 있다

WebGL과 WebGPU에서는 `predict()`가 GPU에 계산 명령을 보낸 뒤, 계산이 끝나기 전에 결과 텐서를 반환할 수 있다.
따라서 `predict()`가 반환됐다고 해서 추론 결과까지 준비된 것은 아니다.
실제 결과를 읽는 `output.data()`는 GPU 계산이 끝날 때까지 기다린다.
이번 실험에서 CPU와 WASM은 `predict()`가 반환되기까지의 시간과 결과를 읽기까지의 시간이 거의 같았다.

한 번의 추론에서 다음 두 시간을 측정했다.

| 이름      | 잰 구간                                                   | 뜻                                     |
| --------- | --------------------------------------------------------- | -------------------------------------- |
| `syncMs`  | `predict()`를 호출한 때부터 반환될 때까지                 | `predict()`가 JavaScript를 점유한 시간 |
| `totalMs` | `predict()`를 호출한 때부터 `output.data()`가 끝날 때까지 | 추론 결과가 준비되기까지의 전체 시간   |

예를 들어 `syncMs`가 1ms이고 `totalMs`가 10ms라면, `predict()`는 JavaScript를 1ms 동안 점유했고 추론 결과는 호출 후 10ms가 지나 준비된 것이다.

백엔드의 추론 속도는 결과가 준비되기까지 걸린 `totalMs`로 비교했다.
`syncMs`는 `predict()`를 호출한 JavaScript가 다른 작업을 시작하지 못하는 시간을 확인하는 데 사용했다.

## 처음 5번을 제외한 반복 추론은 WebGPU가 가장 빨랐다

각 회차에서 처음 5번을 제외한 나머지 45번의 중앙값은 다음과 같았다.
중앙값은 측정값의 절반이 이보다 짧고 나머지 절반이 이보다 길다는 뜻이다.

이 값은 백엔드를 같은 방법으로 비교하기 위한 요약이다. 처음 5번을 제외했다고 해서 실행 시간이
완전히 안정됐다고 가정하지는 않는다.

| 백엔드 | 1회차   | 2회차  | 3회차   | 회차 간 최대 차이 |
| ------ | ------- | ------ | ------- | ----------------- |
| WebGPU | 3.4ms   | 3.5ms  | 3.5ms   | 0.1ms             |
| WebGL  | 10.6ms  | 10.7ms | 10.6ms  | 0.1ms             |
| WASM   | 11.1ms  | 11.1ms | 10.7ms  | 0.4ms             |
| CPU    | 330.5ms | —      | 331.0ms | 0.5ms             |

WebGPU의 추론 결과는 세 회차 모두 3.4\~3.5ms 만에 준비됐다. WebGL과 WASM보다 약 7ms
빨랐다. WebGPU, WebGL, WASM의 중앙값은 모두 앞에서 정한 12.6ms 안에 들었다.

CPU는 한 번의 추론에 약 331ms가 걸렸다. 이 속도로는 16.7ms마다 들어오는 60fps 영상의 모든 프레임을 처리할 수 없다.

WebGL과 WASM의 차이는 0.1\~0.5ms였다. 이는 WASM의 회차 간 차이인 최대 0.4ms와 비슷하다.
따라서 이번 측정만으로는 WebGL과 WASM 중 어느 쪽의 추론 결과가 더 빨리 준비된다고 구분하기 어렵다.

`predict()`가 JavaScript를 점유한 시간은 다음과 같았다.

| 백엔드 | `syncMs` 중앙값 |
| ------ | --------------- |
| WebGPU | 1.1\~1.2ms      |
| WebGL  | 1.4ms           |
| WASM   | 10.7\~11.1ms    |
| CPU    | 약 331ms        |

WebGL과 WASM은 추론 결과가 준비되는 시간은 비슷했지만, `predict()`가 JavaScript를 점유한 시간은 달랐다.
WASM에서는 10.7\~11.1ms 동안 `predict()`가 반환되지 않았다. WebGL에서는 약 1.4ms 뒤에 `predict()`가 반환되고 GPU 계산이 이어졌다.

따라서 WebGL의 추론 결과가 WASM보다 빨리 나온 것은 아니다. 다만 WebGL에서는 결과를 기다리는 동안 JavaScript가 다른 작업을 실행할 수 있었다.
추론을 워커에서 실행한다면, 이 시간에 워커가 새로 들어온 메시지를 처리할 수 있다.

## 첫 추론은 모든 백엔드에서 12.6ms를 넘었다

모델을 불러온 뒤 첫 번째 추론 시간을 따로 측정했다.

| 백엔드 | 첫 추론        | 반복 추론 중앙값 |
| ------ | -------------- | ---------------- |
| WebGPU | 23.1\~25.8ms   | 3.4\~3.5ms       |
| WebGL  | 196.0\~202.9ms | 10.6ms           |
| WASM   | 42.1\~48.3ms   | 10.7\~11.1ms     |
| CPU    | 407.5\~407.7ms | 330.5\~331.0ms   |

모든 백엔드의 첫 추론이 12.6ms 예산을 넘었다. 반복 추론이 가장 빨랐던 WebGPU도 첫 추론에는 23.1\~25.8ms가 걸렸다.

페이지를 새로 열지 않아도 모델을 다시 불러오면 첫 추론은 다시 느려졌다. 모델을 불러온 뒤 실제
카메라 프레임을 받기 전에 추론을 미리 실행하면 가장 큰 첫 실행 지연을 카메라 처리 전에 치를 수
있다. 다만 한 번 실행하는 것만으로 이후 속도가 완전히 일정해지는 것은 아니었다.

이번 실험에서는 첫 추론에 포함된 작업을 따로 측정하지 않아 지연의 원인별 시간은 알 수 없다.

### WebGPU는 첫 추론 뒤에도 약 30회까지 빨라졌다

50번의 추론을 5번씩 묶고 각 구간의 중앙값을 계산했다. 표에는 실행 초반과 후반의 변화를 볼 수
있는 구간만 추렸다. 범위는 백엔드마다 페이지를 새로 연 회차에서 나온 가장 작은 값과 가장 큰
값이다.

| 백엔드 | 1\~5번째       | 6\~10번째      | 21\~25번째     | 46\~50번째     | 마지막 20회 중앙값 |
| ------ | -------------- | -------------- | -------------- | -------------- | ------------------ |
| WebGPU | 4.2\~4.3ms     | 3.8\~4.2ms     | 3.5ms          | 3.3ms          | 3.3ms              |
| WebGL  | 10.5\~10.9ms   | 10.1\~10.2ms   | 10.5ms         | 10.6\~11.0ms   | 10.9\~11.0ms       |
| WASM   | 11.6\~12.0ms   | 10.9\~11.0ms   | 10.7\~11.2ms   | 10.7\~11.1ms   | 10.7\~11.1ms       |
| CPU    | 327.3\~331.7ms | 327.4\~329.4ms | 331.0\~333.0ms | 331.2\~332.1ms | 331.3\~332.1ms     |

WASM과 CPU는 첫 구간 뒤 비슷한 수준을 유지했다. WebGPU는 첫 추론 뒤에도 실행할수록 빨라졌고,
약 30번째부터 3.3\~3.4ms 부근에 가까워졌다. WebGL은 후반 값이 오히려 조금 커져 한 지점을
안정 시점으로 정하기 어려웠다.

따라서 모든 백엔드에 공통으로 “다섯 번 실행하면 준비가 끝난다”고 말할 수 없다. 앞에서 제시한
45회 중앙값은 반복 추론을 비교한 값이며, 정확한 워밍업 종료 시각을 뜻하지 않는다.

## 모델을 불러오는 데 0.9\~3.5초가 걸렸다

모델을 불러오기 시작한 때부터 실행할 준비가 끝날 때까지 걸린 시간을 측정했다.

| 백엔드 | 측정 횟수 | 모델 적재 시간     |
| ------ | --------- | ------------------ |
| WebGPU | 3회       | 860.3\~873.0ms     |
| CPU    | 2회       | 875.4\~895.8ms     |
| WebGL  | 3회       | 874.7\~2,902.5ms   |
| WASM   | 3회       | 2,623.9\~3,478.8ms |

WebGPU와 CPU는 모든 회차에서 약 0.9초가 걸렸다. WebGL은 두 회차에서는 약 0.9초였지만
한 회차에서는 2.9초가 걸렸다. WASM은 모든 회차에서 2.6\~3.5초가 걸렸다.

마지막 측정 회차에서 첫 번째 모델 파일을 요청한 때부터 마지막 응답이 끝날 때까지의 구간을 측정했다.
이 구간과 전체 적재 시간의 차이는 10.2\~14.5ms였다.

다만 모델 파일의 주소가 실행마다 달라 브라우저 캐시를 같은 조건으로 맞추지 못했다. 파일 요청
구간에는 다운로드뿐 아니라 그사이에 실행된 처리도 포함된다. 서버가 상세한 네트워크 시간을
제공하지 않아 다운로드와 모델 생성에 걸린 시간도 분리하지 못했다.

따라서 위 표는 이번 실행에서 관찰한 적재 시간이다. WASM이 WebGPU보다 모델을 느리게
불러온다고 일반화할 수는 없다.

### 같은 로컬 모델을 불러오는 데는 18.7\~30.1ms가 걸렸다

모델 파일을 내려받는 시간과 모델을 실행할 준비를 하는 시간을 구분하기 위해, 모델을 브라우저의 IndexedDB에 미리 저장했다.
이후 같은 모델을 사용해 백엔드마다 적재 시간을 세 번씩 측정했다.

| 백엔드 | 가장 짧은 시간 | 중앙값 | 가장 긴 시간 |
| ------ | -------------- | ------ | ------------ |
| WebGPU | 22.9ms         | 24.6ms | 25.0ms       |
| WebGL  | 20.4ms         | 24.2ms | 26.3ms       |
| WASM   | 26.7ms         | 29.1ms | 30.1ms       |
| CPU    | 18.7ms         | 25.4ms | 25.9ms       |

이 시간에는 IndexedDB에서 모델을 읽고 그래프와 가중치 텐서를 만드는 작업이 포함된다. 인터넷에서
파일을 받는 시간은 포함되지 않는다.

WebGPU, WebGL, CPU의 범위는 서로 겹쳤다. WASM은 세 번 모두 WebGPU보다 느렸지만 차이는
1.7\~7.2ms였다. 표본이 백엔드마다 세 번뿐이므로 전체 백엔드의 적재 속도 순위를 정하지 않았다.

원격 모델을 불러왔을 때 관찰한 0.9\~3.5초와 비교하면, 같은 로컬 사본을 불러오는 데는
18.7\~30.1ms가 걸렸다. 따라서 원격 적재 시간의 큰 변동은 백엔드 계산보다 모델 파일 요청 조건의
영향을 크게 받았다고 볼 수 있다.

## 전처리와 추론을 합친 시간을 측정했다

앞선 실험에서는 모델의 추론 시간만 측정했다.
실제 처리 과정에서는 한 워커가 프레임을 모델 입력으로 바꾼 뒤 추론하고 결과까지 읽는다. 이 전체 과정에 걸리는 시간을 별도로 측정했다.

입력 조건을 같게 유지하기 위해 카메라 대신 1920×1080 캔버스에서 동일한 이미지를 만들고
`VideoFrame`으로 변환했다. 이후 이를 캔버스 프레임이라고 부른다.
캔버스 프레임은 워커에 전달했다.
워커에서는 다음 세 조건을 각각 50번 실행했다.

| 조건 | 측정한 작업                                   |
| ---- | --------------------------------------------- |
| A    | `VideoFrame`을 모델 입력값이 담긴 배열로 변환 |
| B    | 배열로 텐서를 만들고 추론한 뒤 결과를 읽음    |
| C    | A와 B의 작업을 차례로 모두 실행               |

B와 C는 모두 반복할 때마다 텐서를 새로 만들었다. B에서 텐서를 재사용하면 C보다 작업이 하나
줄어들어 두 조건을 공정하게 비교할 수 없기 때문이다.

바로 앞에서 실행한 작업이 다음 측정에 미치는 영향을 한 조건에 몰지 않도록 실행 순서를 반복마다 바꿨다.

```text
A → B → C
B → C → A
C → A → B
```

CPU는 모델 추론만 약 331ms가 걸렸기 때문에 이 실험에서 제외했다.

## 전처리까지 포함해도 WebGPU가 가장 빨랐다

각 조건을 두 차례 측정했다. 표에서 `/`로 구분한 두 값은 각 회차의 중앙값이다. p95는
측정값의 95%가 이 시간 안에 끝났다는 뜻이다.

워커 점유 시간은 전처리를 시작한 때부터 `predict()`가 반환될 때까지다.

| 백엔드 | A 입력 변환 | B 텐서 생성과 추론 | C 전체 처리   | C의 p95       | C의 워커 점유 시간 |
| ------ | ----------- | ------------------ | ------------- | ------------- | ------------------ |
| WebGPU | 1.7 / 1.3ms | 4.2 / 3.7ms        | 5.8 / 5.0ms   | 6.5 / 5.3ms   | 2.9 / 2.4ms        |
| WASM   | 1.5 / 1.5ms | 10.9 / 10.9ms      | 12.3 / 12.2ms | 13.2 / 13.1ms | 12.3 / 12.2ms      |
| WebGL  | 2.2 / 2.4ms | 11.9 / 12.2ms      | 13.9 / 14.4ms | 15.3 / 15.4ms | 3.7 / 4.2ms        |

캔버스 프레임을 모델 입력으로 바꾸고 추론 결과를 읽기까지 WebGPU는 5.0\~5.8ms가 걸렸다.
WASM은 12.2\~12.3ms, WebGL은 13.9\~14.4ms였다. 캔버스 프레임을 사용한 이번 조건에서는
WebGPU가 가장 빨랐다.

p95도 WebGPU가 5.3\~6.5ms로 가장 짧았다. WASM은 13.1\~13.2ms, WebGL은
15.3\~15.4ms였다. 세 백엔드 모두 p95가 16.7ms보다 짧았지만, 이는 카메라가 아닌 캔버스
프레임으로 측정한 결과다.

WASM에서는 전체 처리 시간과 워커 점유 시간이 같았다. 전체 처리가 끝날 때까지 워커가 다른
JavaScript를 실행하지 못했다는 뜻이다. WebGPU와 WebGL에서는 GPU가 계산하는 동안 워커가
다른 작업을 실행할 수 있어 워커 점유 시간이 전체 처리 시간보다 짧았다.

캔버스 프레임의 전처리는 1.3\~2.4ms가 걸렸다. 앞선 실험에서 실제 카메라 프레임을 전처리한
4.1ms보다 짧았다. 입력이 서로 다르므로 이번 전체 처리 시간을 실제 카메라 프레임에 그대로
적용할 수 없다. 실제 카메라 입력에서 결과가 얼마나 자주 나오는지는 연속 입력을 사용하는
다음 실험에서 확인한다.

## 전처리와 추론을 함께 실행해도 중앙값은 늘지 않았다

전처리와 추론을 따로 실행한 시간의 합을 두 작업을 함께 실행한 시간과 비교했다. 함께 실행해서
추가된 시간은 다음과 같이 계산했다.

```text
추가 시간 = C 전체 처리 - (A 입력 변환 + B 텐서 생성과 추론)
```

추가 시간이 양수이면 두 작업을 함께 실행했을 때 더 오래 걸렸다는 뜻이다. 0이면 각각 실행한
시간의 합과 같고, 음수이면 함께 실행한 시간이 더 짧게 측정됐다는 뜻이다.

각 반복에서 추가 시간을 먼저 계산한 뒤 중앙값과 p95를 구했다. 표에서 `/`로 구분한 값은
1회차와 2회차 결과다.

| 백엔드 | 추가 시간 중앙값 | 추가 시간 p95 | 전체 범위   | 음수 횟수 |
| ------ | ---------------- | ------------- | ----------- | --------- |
| WebGPU | -0.2 / 0.0ms     | 0.5 / 0.3ms   | -2.3\~1.7ms | 27 / 22회 |
| WASM   | -0.2 / -0.1ms    | 0.3 / 0.3ms   | -1.7\~0.5ms | 31 / 24회 |
| WebGL  | -0.1 / -0.3ms    | 1.4 / 1.5ms   | -2.2\~2.3ms | 25 / 26회 |

각 회차는 45번의 측정값으로 계산했다. 추가 시간의 중앙값은 -0.3\~0ms였다. 따라서 전처리와
추론을 함께 실행했을 때 중앙값이 늘어나는 현상은 나타나지 않았다.

다만 모든 측정값이 0에 가까웠던 것은 아니다. WebGL의 추가 시간은 p95에서 1.4\~1.5ms였고,
개별 측정값은 최대 2.3ms까지 나왔다. 반대로 추가 시간이 음수인 경우도 많았다. 이는 함께
실행하면 실제 작업 시간이 줄어든다는 뜻이 아니라, 측정 시점과 실행 순서에 따라 시간이
흔들렸다는 뜻이다.

실행 순서별 중앙값은 -0.9\~0.2ms였다. C → A → B 순서가 여섯 회차 중 다섯 회차에서 가장
작았고, 한 회차에서는 순서에 따라 최대 1.1ms 차이가 났다. 따라서 실행 순서의 영향이 전혀
없었다고 단정할 수는 없다.

## 세 백엔드의 출력 차이는 작았고 텐서 수는 늘지 않았다

같은 캔버스 프레임을 WebGPU, WebGL, WASM으로 처리한 뒤 출력값을 비교했다.
세 백엔드 모두 1,001개의 값을 출력했다. WebGPU를 기준으로 비교했을 때 출력값의 최대 차이는
WebGL이 4.77×10⁻⁶, WASM이 2.26×10⁻⁵였다.

추론을 50번 반복하기 전과 후에는 TensorFlow.js가 관리하는 텐서 수를 비교했다.
입력과 출력 텐서는 각 반복이 끝날 때마다 `dispose()`로 해제했으며, 모든 실행에서 텐서 수가 증가하지 않았다.

따라서 이번 실험에서는 백엔드에 따른 큰 출력 차이나 TensorFlow.js 텐서가 반복해서 쌓이는 현상이 나타나지 않았다.

## 다음 실험에서는 WebGPU를 우선 사용한다

이번 측정에서는 모델만 실행한 시간과 전처리를 포함한 전체 처리 시간이 모두 WebGPU에서 가장
짧았다. 모델만 실행했을 때는 3.4\~3.5ms, 캔버스 프레임의 전처리까지 포함했을 때는
5.0\~5.8ms가 걸렸다. 전체 처리 시간의 p95도 5.3\~6.5ms로 가장 짧았다.

WebGPU가 워커를 점유한 시간은 2.4\~2.9ms였다. 추론 결과가 빠르게 나왔을 뿐 아니라,
GPU가 계산하는 동안 워커가 다른 작업을 처리할 수도 있었다. 이 결과를 바탕으로 다음 연속 입력
실험에서는 WebGPU를 우선 사용한다.

WebGL과 WASM은 장단점이 달랐다. WebGL은 워커를 점유하는 시간이 3.7\~4.2ms로 짧았지만
전체 처리 시간은 13.9\~14.4ms였다. WASM은 전체 처리 시간이 12.2\~12.3ms로 WebGL보다
짧았지만, 작업이 끝날 때까지 워커를 점유했다. WebGL과 WASM은 호환성이 필요할 때 검토할 후보로 남겼다.

## 이번 실험에서 확인하지 못한 것

- Apple M4가 탑재된 Mac과 Chrome 151에서만 측정했다. 다른 기기와 브라우저에서도 백엔드의 속도 순서가 같은지는 알 수 없다.
- MobileNet v2 한 모델만 사용했다. 다른 모델에서도 WebGPU가 가장 빠른지는 확인하지 않았다.
- 전처리와 추론을 합친 실험에서는 카메라가 아닌 캔버스 프레임을 사용했다. 실제 카메라 프레임의 전체 처리 시간은 측정하지 않았다.
- CPU는 모델 추론만 약 331ms가 걸려 전처리와 추론을 합친 실험에서 제외했다.
- 첫 추론이 느려진 원인을 작업별로 나누어 측정하지 않았다.
- 처음 방문해 원격 모델을 받는 시간은 네트워크 상태에 따라 달라진다. IndexedDB의 같은 사본을 불러오는 시간은 별도로 비교했다.
- 한 프레임의 전처리와 추론을 차례로 실행했다. 한 프레임을 추론하는 동안 다음 프레임을 미리 전처리하는 방식은 비교하지 않았다.
- 실제 카메라 입력에서 분석 결과가 얼마나 늦게 나오고 얼마나 자주 갱신되는지는 측정하지 않았다. 최신 프레임만 남기는 방식의 효과는 다음 실험에서 확인한다.

## 다음에는 오래된 프레임이 쌓이지 않는지 확인한다

이번 실험에서는 입력 한 장의 처리 시간만 측정했다. 실제 카메라는 이전 프레임의 처리가 끝나지
않아도 다음 프레임을 계속 보낸다. 모델이 이 속도를 따라가지 못하면 처리할 프레임이 쌓인다.

예를 들어 첫 번째 프레임을 처리하는 동안 두 번째, 세 번째, 네 번째 프레임이 들어올 수 있다. 이
프레임을 모두 저장하면 첫 번째 처리가 끝난 뒤 두 번째부터 차례로 처리한다. 그러면 분석 결과가
현재 화면보다 점점 늦어진다.

다음 실험에서는 워커가 바쁜 동안 가장 최근에 들어온 프레임 하나만 남긴다. 위 예에서는 두 번째와
세 번째 프레임을 건너뛰고 네 번째 프레임을 다음에 처리한다. 일부 프레임은 분석하지 않지만,
오래된 프레임이 계속 쌓이지 않는다.

처리 시간을 일부러 16.7ms보다 길게 만들어 다음을 확인한다.

- 몇 장을 받았고, 처리했고, 건너뛰었는가
- 처리할 프레임이 몇 장이나 쌓였는가
- 프레임을 받은 뒤 결과가 나오기까지 얼마나 걸렸는가
- 화면의 분석 결과가 얼마나 자주 바뀌었는가

처리가 늦어져도 대기 중인 프레임은 한 장을 넘지 않아야 한다. 느려지게 만든 조건을 제거하면 곧
가장 최근 프레임을 처리해야 한다. 이 두 조건을 만족하면 프레임을 모두 처리하지 않더라도 분석
결과가 현재 영상에서 계속 멀어지는 일은 막을 수 있다.
